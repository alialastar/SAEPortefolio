AC21.01 · Compétence Administrer

Configurer et dépanner le routage dans un réseau

Preuve — TD ACL étendues (R3.01 Réseaux de campus)

Contexte

TD réalisé dans le cadre du module R3.01. Objectif : sécuriser le trafic d'un réseau d'entreprise segmenté en VLANs à l'aide de listes de contrôle d'accès étendues. Infrastructure simulée : deux routeurs Cisco (R1, R2), deux commutateurs (S1, S2) et deux PC répartis sur trois VLANs — Gestion (VLAN 20), Opérations (VLAN 30), Ventes (VLAN 40). R1 assure le routage inter-VLAN en mode router-on-a-stick.

Savoirs mis en œuvre

ACL étendues Inter-VLAN 802.1Q Trunking SSH / HTTP / HTTPS / ICMP Cisco IOS

Placement des ACL : une ACL étendue doit être appliquée au plus près de la source. Filtrage par protocole (TCP, UDP, ICMP), adresse source/destination et numéro de port.

Résultats des tests de vérification

  • PC-A → ping Ventes (10.40.0.10) : BLOQUÉ ✓
  • PC-A → ping Gestion (10.20.0.1) : Autorisé ✓
  • PC-B → ping Opérations (10.30.0.10) : BLOQUÉ ✓
  • PC-B → ping Gestion (10.20.0.1) : BLOQUÉ ✓
  • PC-B → ping Loopback R1 (172.16.1.1) : Autorisé ✓
  • PC-B → HTTPS Gestion : BLOQUÉ ✓
  • PC-B → HTTPS Loopback : Autorisé ✓
  • PC-B → SSH R2 (10.20.0.4) : BLOQUÉ ✓
  • PC-B → SSH Loopback : Autorisé ✓

Problèmes rencontrés & solutions

Problème 1 — Sens d'application ACL

Confusion inbound/outbound : une ACL appliquée en outbound sur la mauvaise sous-interface ne filtrait pas le trafic attendu.

Solution : retracer le chemin du paquet depuis la source pour identifier la bonne interface et le bon sens (inbound sur la sous-interface du VLAN source).

Problème 2 — Ordre des règles ACL

Un permit any placé trop haut dans la liste neutralisait les règles deny suivantes.

Solution : placer systématiquement les règles deny spécifiques avant tout permit any.

Analyse réflexive — Modèle de Gibbs

Description : Configuration de quatre ACL étendues nommées sur R1 pour implémenter des politiques de sécurité précises entre les VLANs Gestion, Opérations et Ventes.

Ressenti : L'infrastructure (VLANs, trunks, routage inter-VLAN) s'est bien passée. La difficulté est venue sur les ACL : je ne savais pas toujours sur quelle interface les appliquer ni dans quel sens.

Analyse : Je configurais sans modéliser le flux avant. Une fois le réflexe pris de me demander "d'où vient le paquet, par quelle interface entre-t-il ?", les erreurs ont disparu. L'ordre des règles dans une ACL est critique.

Plan d'action : Rédiger les règles dans un tableau (source / destination / protocole / action) avant de les saisir. Pratiquer sur des topologies plus complexes pour automatiser ce raisonnement — compétence directement utile en entreprise pour sécuriser un réseau.

AC21.06 · Compétence Administrer

Travailler en équipe pour développer ses compétences professionnelles

Preuve — Gestion d'incident fibre en NOC (Alternance)

Contexte

En période d'entreprise, j'ai travaillé sur la gestion des désécurisations sur le périmètre IP. Ces interventions mobilisent plusieurs acteurs : techniciens terrain, superviseurs réseau et support pour les cas complexes. Le travail en équipe est indispensable à la résolution des incidents.

Cas concret — Incident liaison fibre

Souci détecté sur la liaison 75BRU1-SWAGR-1S XGigabitEthernet2/0/3 → 75lau1-nro-1 Port 2/4. Ticket créé via ALARM MANAGER. Diagnostic initial : statut administratif UP mais statut réel DOWN sur le port.

Diagnostic relevé

L'équipement distant recevait -33 dBm (proche de -40 dBm = forte dégradation). Malgré l'envoi de signal par l'équipement A, l'équipement B ne recevait rien — suspicion de coupure fibre.

Actions menées

Déclenchement du mainteneur contractuel. Pilotage de l'intervention terrain de A à Z : guidage du technicien en s'appuyant sur la ROP (Route Optique) pour localiser les boîtes et vérifier le parcours de la fibre. Coordination avec les collègues pour la surveillance post-intervention en cas de récidive.

Compétences mobilisées

Supervision réseau Pilotage intervention Lecture ROP Trouble ticket Travail en équipe

Analyse réflexive — Modèle de Gibbs

Description : Résolution d'un incident de liaison fibre en NOC, de la création du ticket jusqu'au pilotage de l'intervention terrain, en collaboration avec l'équipe.

Ressenti : De manière générale, le processus se passe bien. Je sais d'emblée vers quels acteurs me tourner, quelle équipe de techniciens déclencher, si le support est nécessaire.

Difficultés identifiées : J'ai du mal à transmettre les informations au bon vocabulaire technique lors des passations entre shifts. Je rencontre aussi des difficultés à piloter les cas complexes où les choses ne se passent pas comme prévu (module changé sans retour de signal, technicien qui ne retrouve pas les boîtes).

Plan d'action : Prendre plus d'interventions, solliciter mes collègues pour m'aider au pilotage dans les cas difficiles, et travailler le vocabulaire technique pour être plus efficace lors des passations.

AC23.01 · Compétence Automatiser

Automatiser l'administration système avec des scripts

Preuve — Module R4.05 · Bash & Ansible

Contexte

Module R4.05 (4h CM, 9h TD, 12h TP). Objectif : automatiser des tâches d'administration système Linux via des scripts Bash avancés et Ansible. Les TPs se déroulaient sur des machines Ubuntu, en lien direct avec des scénarios d'administration réels.

Savoirs mis en œuvre

Bash avancé Expressions régulières grep / sed / awk cron / crontab Ansible Playbooks YAML Rôles Ansible

Tâches réalisées & résultats

  • Script Bash — création d'utilisateurs depuis CSV : Fonctionnel
  • Script monitoring de service avec alerte dans les logs : Fonctionnel
  • Analyse de logs avec grep/awk/sed : Fonctionnel
  • Planification cron — sauvegarde quotidienne : Validée
  • Inventaire Ansible + connectivité SSH sans mot de passe : Validés
  • Playbook déploiement Apache avec handler de redémarrage : Fonctionnel
  • Playbook multi-distributions Debian/RedHat : Fonctionnel
  • Structuration via rôles Ansible : Réalisée

Problèmes rencontrés & solutions

Problème 1 — Shebang Bash vs sh

Un script fonctionnait avec bash mais échouait avec sh.

Solution : vérifier le shebang (#!/bin/bash) et déboguer avec bash -x.

Problème 2 — SSH Ansible (Permission denied)

Ansible ne pouvait pas se connecter aux nœuds gérés.

Solution : la clé SSH publique n'avait pas été copiée. Utilisation de ssh-copy-id puis vérification avec ansible all -m ping.

Problème 3 — Expressions régulières grep

Certains patterns non reconnus avec grep standard.

Solution : confusion entre grep (ERE désactivé par défaut) et grep -E. Passage à grep -E ou egrep.

Analyse réflexive — Modèle de Gibbs

Description : Automatisation de tâches d'administration Linux via Bash et Ansible — gestion d'utilisateurs, monitoring, analyse de logs, déploiement Apache multi-distributions.

Ressenti & déclic : Bash était déjà un peu connu, mais les scripts avancés (gestion des erreurs, codes de retour, expressions régulières) m'ont demandé plus de temps. Le déclic : comprendre que chaque commande Linux retourne un code de retour testable — c'est ce qui permet d'écrire des scripts robustes.

Analyse : Les erreurs venaient souvent d'un manque de rigueur sur les détails (variable mal nommée, indice de tableau). L'automatisation exige plus de précision que la configuration manuelle : une erreur dans un script se reproduit sur toutes les machines. La logique d'idempotence d'Ansible est un vrai changement de paradigme.

Plan d'action : Tester les scripts sur un environnement isolé avant tout déploiement (--check --diff avec Ansible, bash -n pour la syntaxe). Approfondir les rôles Ansible pour structurer des projets réutilisables. Ce module est directement en lien avec mon alternance : l'automatisation de tâches répétitives est au cœur des pratiques NOC.

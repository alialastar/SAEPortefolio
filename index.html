AC21.04 · Compétence Administrer

Déployer des services réseau avancés

Preuve — Projet R3.03 · Services réseau avancés
📄 Preuve 🔍 Analyse réflexive

Contexte

Projet réalisé sur 4 séances de TP (15h) dans le cadre du module R3.03. Déploiement d'une infrastructure complète de services réseau sur des VMs Windows Server 2016 hébergées sur vCenter. Trois services couverts : DNS (redondance + délégation de zone), accès distant RDS (Remote Desktop Web Access), et messagerie (hMailServer). Machines intégrées au domaine Active Directory peda.rt.local.

Savoirs mis en œuvre

DNS / zones / enregistrements SMTP / POP3 / IMAP RDS / RemoteApp Active Directory Windows Server 2016 Wireshark

Résultats

  • Résolution DNS interne et externe : Fonctionnelle
  • Redondance DNS primaire/secondaire — transfert de zone : Validé
  • Délégation de sous-domaine : Validée par nslookup
  • Connexions RDS simultanées (>2) : Validées
  • Remote Desktop Web Access + RemoteApp (Thunderbird, Wireshark) : Fonctionnel
  • Envoi/réception mail interne et externe (tp.rt) : Fonctionnel
  • Client POP3 vs IMAP — différences observées et documentées

Problèmes rencontrés & solutions

Problème 1 — Transfert de zone DNS

Le transfert vers le secondaire échouait — zone non répliquée.

Solution : l'autorisation de transfert n'était pas activée sur le primaire. Ajout de l'IP du secondaire dans les paramètres de transfert.

Problème 2 — Mails externes non reçus

L'enregistrement MX pointait vers un alias CNAME au lieu d'un enregistrement A direct.

Solution : correction de l'enregistrement MX pour pointer directement vers l'IP du serveur de messagerie.

Problème 3 — Limite 2 sessions RDS

Impossible de dépasser 2 connexions simultanées.

Solution : le serveur de licences CAL (RCLicencespeda) n'était pas déclaré dans la configuration RDS. Ajout manuel du serveur de licences.

Synthèse réflexive — Modèle de Gibbs

Description : Déploiement d'une infrastructure DNS redondante, d'un service RDS avec RemoteApp et d'un serveur de messagerie hMailServer sur Windows Server 2016, en binôme sur 4 séances.

Ressenti : Projet stimulant mais exigeant par la multiplicité des services. Satisfaction réelle lors des premières validations (échange de mails, délégation DNS), frustration lors des blocages dont la cause n'était pas immédiatement identifiable.

Analyse : L'organisation séance par séance et la rigueur de documentation ont facilité le diagnostic. J'ai appris que chaque service a ses propres paramètres de sécurité à configurer explicitement, et que les enregistrements MX ne doivent jamais pointer vers un CNAME.

Plan d'action : Systématiser la lecture des prérequis avant tout déploiement, vérifier les dépendances entre services (DNS → messagerie). Approfondir Active Directory et les GPO, directement applicables en alternance.

AC21.06 · Compétence Administrer

Travailler en équipe pour développer ses compétences professionnelles

Preuve — Gestion d'incident fibre en NOC (Alternance)
📄 Preuve 🔍 Analyse réflexive

Contexte

En période d'entreprise, j'ai travaillé sur la gestion des désécurisations sur le périmètre IP. Ces interventions mobilisent plusieurs acteurs : techniciens terrain, superviseurs réseau et support pour les cas complexes. Le travail en équipe est indispensable à la résolution des incidents.

Cas concret — Incident liaison fibre

Souci détecté sur la liaison 75BRU1-SWAGR-1S XGigabitEthernet2/0/3 → 75lau1-nro-1 Port 2/4. Ticket créé via ALARM MANAGER. Diagnostic initial : statut administratif UP mais statut réel DOWN sur le port.

Diagnostic relevé

L'équipement distant recevait -33 dBm (proche de -40 dBm = forte dégradation). Malgré l'envoi de signal par l'équipement A, l'équipement B ne recevait rien — suspicion de coupure fibre.

Actions menées

Déclenchement du mainteneur contractuel. Pilotage de l'intervention terrain de A à Z en s'appuyant sur la ROP (Route Optique) pour localiser les boîtes et vérifier le parcours de la fibre. Coordination avec les collègues pour la surveillance post-intervention.

Supervision réseau Pilotage intervention Lecture ROP Trouble ticket Travail en équipe

Synthèse réflexive — Modèle de Gibbs

Description : Résolution d'un incident de liaison fibre en NOC, de la création du ticket jusqu'au pilotage de l'intervention terrain, en collaboration avec l'équipe.

Ressenti : De manière générale, le processus se passe bien. Je sais d'emblée vers quels acteurs me tourner, quelle équipe déclencher, si le support est nécessaire.

Difficultés : Mal à transmettre les informations au bon vocabulaire technique lors des passations entre shifts. Difficultés à piloter les cas complexes où les choses ne se passent pas comme prévu.

Plan d'action : Prendre plus d'interventions, solliciter les collègues pour le pilotage dans les cas difficiles, et travailler le vocabulaire technique pour être plus efficace lors des passations.

AC23.01 · Compétence Automatiser

Automatiser l'administration système avec des scripts

Preuve — Module R4.05 · Bash & Ansible
📄 Preuve 🔍 Analyse réflexive

Contexte

Module R4.05 (4h CM, 9h TD, 12h TP). Automatisation de tâches d'administration système Linux via Bash avancé et Ansible. TPs sur machines Ubuntu, en lien direct avec des scénarios d'administration réels.

Savoirs mis en œuvre

Bash avancé Expressions régulières grep / sed / awk cron / crontab Ansible Playbooks YAML Rôles Ansible

Tâches réalisées & résultats

  • Script Bash — création d'utilisateurs depuis CSV : Fonctionnel
  • Script monitoring de service avec alerte dans les logs : Fonctionnel
  • Analyse de logs avec grep/awk/sed : Fonctionnel
  • Planification cron — sauvegarde quotidienne : Validée
  • Inventaire Ansible + connectivité SSH sans mot de passe : Validés
  • Playbook déploiement Apache avec handler : Fonctionnel
  • Playbook multi-distributions Debian/RedHat : Fonctionnel
  • Structuration via rôles Ansible : Réalisée

Problèmes rencontrés & solutions

Problème 1 — Shebang Bash vs sh

Script fonctionnel avec bash mais échouait avec sh.

Solution : vérifier le shebang (#!/bin/bash) et déboguer avec bash -x.

Problème 2 — SSH Ansible (Permission denied)

Ansible ne pouvait pas se connecter aux nœuds gérés.

Solution : clé SSH publique non copiée. Utilisation de ssh-copy-id puis vérification avec ansible all -m ping.

Problème 3 — Expressions régulières grep

Certains patterns non reconnus avec grep standard.

Solution : passage à grep -E pour activer les ERE.

Synthèse réflexive — Modèle de Gibbs

Description : Automatisation de tâches d'administration Linux via Bash et Ansible — gestion d'utilisateurs, monitoring, analyse de logs, déploiement Apache multi-distributions.

Ressenti & déclic : Bash était déjà un peu connu, mais les scripts avancés m'ont demandé plus de temps. Le déclic : chaque commande Linux retourne un code de retour testable — c'est ce qui permet d'écrire des scripts robustes.

Analyse : Les erreurs venaient souvent d'un manque de rigueur sur les détails. L'automatisation exige plus de précision que la configuration manuelle : une erreur dans un script se reproduit sur toutes les machines. La logique d'idempotence d'Ansible est un vrai changement de paradigme.

Plan d'action : Tester les scripts sur un environnement isolé avant déploiement (--check --diff avec Ansible). Approfondir les rôles Ansible. Ce module est directement en lien avec mon alternance.
